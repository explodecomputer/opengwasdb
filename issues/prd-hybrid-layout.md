# PRD: Hybrid Layout — Dense Component + Ragged Overflow

Design basis: `docs/adr/0026-hybrid-layout-dense-ragged-overflow.md`.

## Problem Statement

Heterogeneous genome-wide collections — OpenGWAS `ieu-a` / `ieu-b`, i.e.
independent consortia GWAS — fit neither existing layout. Their Analyses were
imputed to **different panels**, so the source-observed union of variants
(plausibly 50–100M+) is far larger than any single reference panel, but each
Analysis is genome-wide and they **share a large common core** with a
heterogeneous, study-specific long tail.

- A **Dense** store of the whole union (ADR 0022's rule) inflates the variant
  axis several-fold with mostly-NaN rows that are **never imputable** (off-panel
  variants have no reference LD structure) — every dense query then pays for a
  much larger variant axis, tabix index, and ALID mmap for no benefit.
- A **Ragged** store wastes an explicit `variant_index` (4 bytes) on **every**
  association, including the common-core variants that appear in most studies —
  storing the same common variant's index once per study.

There is no layout that stores the common/imputable core densely and the
study-specific tail raggedly in one queryable, completable store.

## Solution

Introduce a **Hybrid Layout** (a third `PrimaryStorageLayout`): a single
integrated Store holding two Query Components over one shared Store Variant
Table (see CONTEXT.md `Hybrid Layout`):

- **Dense Component** — a dense matrix whose variant axis is the **completion
  reference panel** (the imputable set).
- **Ragged Overflow Component** — a CSR store of each Analysis's **off-panel
  observed** associations. Always observed, never imputed.

A variant is on-panel (a Dense Component row) *xor* off-panel (a Ragged Overflow
entry), so the two components partition each Analysis's associations disjointly.
The store is **generated by extending the two-pass dense VCF builder** — each
study read once, routing on-panel variants to the dense fill and off-panel
variants to the ragged CSR. **Reference Completion targets only the Dense
Component**, reusing the dense completion pipeline unchanged. Queries unify both
components behind one result. This deliberately reopens — as a scoped new layout,
not a reversal — the Dense+Overflow design that ADR 0022 deleted for the
shared-panel case (see ADR 0026 for the scope boundary).

## User Stories

1. As a data engineer, I want to build one store from a heterogeneous genome-wide
   collection given a reference panel, so that common/imputable variants are dense
   and study-specific variants are ragged, without choosing per-study manually.
2. As a data engineer, I want each study read only once during the build, so that
   generation cost is close to the existing dense build rather than double.
3. As a data engineer, I want the build to route each variant to dense (on-panel)
   or ragged (off-panel) by membership in the supplied reference panel, so that
   "dense" means exactly "imputable".
4. As a data engineer, I want one shared Store Variant Table covering panel ∪
   off-panel-observed variants, so both components reference a single
   `variant_index` space.
5. As a researcher, I want a query for a variant × analysis to return the right
   association whether it lives in the dense matrix or the overflow, transparently.
6. As a researcher, I want `analysis`, `phewas`, `range_phewas`, `top_hits`, and
   `lookup` to return the union of both components with correct
   `association_status`, so I never miss an off-panel association.
7. As a researcher, I want on-panel (common) PheWAS to stay fast (served by the
   dense component), accepting that off-panel rare-variant PheWAS may be slower.
8. As a data engineer, I want to reference-complete a Hybrid store and have only
   the Dense Component imputed, with the overflow left observed-only, so the
   completed store is correct and the overflow needs no LD logic.
9. As a developer, I want `opengwasdb validate` to check a Hybrid store — both
   components, the shared variant table, and the disjoint-partition invariant
   (on-panel variants never appear in the overflow; off-panel variants are never
   dense rows) — so a malformed hybrid store is caught.
10. As a data engineer, I want a `build-hybrid` CLI command taking a VCF manifest
    and a reference panel, so hybrid generation can be scripted.
11. As a data engineer, I want the hybrid build to reuse the band-streamed,
    process-parallel machinery of the dense build, so it runs at genome scale
    within bounded memory.
12. As a developer, I want the store to declare `PrimaryStorageLayout = hybrid`
    and `AssociationCoverage = full`, so downstream tools dispatch correctly and
    know no source association was dropped.
13. As a researcher/developer, I want a **storage + query benchmark** comparing a
    Hybrid store against a Dense-of-union store built from the same collection, so
    the layout's storage and latency trade-offs are evidenced **before** the design
    is built out further.
14. As a developer, I want the Hybrid build and query to **compose the existing
    dense and ragged components** — the two-pass VCF builder, `RaggedCSRWriter`,
    the dense `StoreQuery` and `RaggedStoreQuery`, the dense completion pipeline,
    and the dense/ragged top-hit indexes — rather than reimplement them, so the
    layout is a thin integration layer over proven code.

## Implementation Decisions

### Representation

One integrated store (single manifest, identity, and Store Variant Table). The
manifest declares `primary_layout = hybrid`. The store contains both a
`data.zarr` dense matrix (Dense Component) and a `data.zarr/ragged` CSR (Ragged
Overflow Component). The variant table is the union of reference-panel variants
and off-panel observed variants; both components index into it (ADR 0026).

### Partition

Dense axis = the reference panel variant list (fixed up front). On-panel source
associations fill the dense matrix; off-panel source associations go to the
overflow. Disjoint by construction — no cross-component dedup.

### Generation

Extend the two-pass dense VCF builder, each study read once:
- **Pass 1**: liftover each study's variants, test panel membership, collect the
  off-panel union. The panel axis needs no union pass (it is given).
- **Pass 2**: band-stream the dense fill for on-panel variants (reuse the existing
  spill + band-write machinery, ADR 0024) and emit each study's off-panel
  `(variant_index, z, se)` into the ragged CSR in the same read.

### Completion

Reference Completion runs on the Dense Component only, reusing the dense
completion pipeline (ADR 0022/0023). The overflow is permanently observed-only.

### Query

Dispatch by panel membership: on-panel variant → dense row/column read; off-panel
variant → ragged access; results concatenated with `association_status`. Off-panel
PheWAS inherits the ragged O(n) scan (variant-centric overflow index deferred).

### Validation

Validate both components independently plus the hybrid invariants: shared variant
table covers both components' indices; on-panel variants (dense rows) never appear
in the overflow; overflow variants are all off-panel; overflow associations are
all `observed`.

### Component reuse (modularity)

The Hybrid Layout is a **thin integration layer**, not new storage machinery. It
must compose existing components:
- **Build**: reuse the dense two-pass builder's liftover, disk-spill, band-write,
  and fork-pool machinery (ADR 0024) for the Dense Component, and `RaggedCSRWriter`
  for the overflow — the only new logic is per-variant on-panel/off-panel routing
  in the passes both components already share.
- **Query**: the hybrid facade dispatches to the existing dense `StoreQuery` and
  `RaggedStoreQuery` per component and concatenates; it does not reimplement
  matrix or CSR reads.
- **Completion**: reuse the dense completion pipeline unchanged on the Dense
  Component.
- **Top-hits**: reuse the dense and ragged top-hit index builders/readers and
  merge their ranked results.

## Out of Scope

- Frequency-threshold partitioning (dense anchored to the panel instead — ADR 0026).
- A variant-centric overflow index for fast off-panel PheWAS (deferred).
- Two-separate-stores packaging (single integrated store — ADR 0026).
- Non-genome-wide / cis-only collections (already served by Ragged Layout).
- Completing or imputing the overflow.
- Genome-scale generation on a real `ieu-a` / `ieu-b` collection — deferred until
  the storage/query benchmark validates the approach on a controlled dataset.
